# 需求与特征结构化

## 1. 适用范围

处理 `search`（按需求检索）的规格。`lookup`（按号取文献）由程序根据用户号码直接建立规格，正常路径不调用本 Skill。只把用户原意变成可执行条件，不检索、不作新颖性或侵权结论。L2 边界是用户授权的主题、日期、国家和文献范围；L3 目标是把原始需求变成待确认或可调度的规格。

## 2. 输入要求

- 新任务：读取当前运行最新的 `data/runs/<run_id>/agent_task.json`，确认 `stage` 为 `SPEC`；读取其中 `input.request`、`input.spec`（存在时）和 `output_schema`。
- 修改任务：只在用户明确要求修改既有条件时，运行 `python run.py show <run_id>` 读取数据库中的最新 `spec` 与原请求；只改指定条件，保留其他字段。此入口不用伪造 SPEC 任务包。
- 缺少原始需求、任务包与实际阶段不一致，或无法确定最新版：停止写入，报告具体缺项。歧义写入 `needs_human`，不能编造答案。

## 4. 执行步骤

1. 确认本次处理属于 `search`，采用请求中用户选择的 `新颖性`、`全景` 或 `侵权风险` 意图，不擅自切换。若错误分派了 `lookup`，报告路由问题，不自行添加技术特征或筛选条件。
2. 把技术内容拆成可对照的 `F1…Fn`。保留数量、先后、因果、连接、阈值与联合触发关系；同义表述不重复造特征。条件修改时保留未改特征的 `fid`。
3. 区分硬条件与偏好。只有用户明确要求的必要条件进入 `hard`，其余进入 `soft`；不得以“可能更相关”为由增加硬条件。按用户语义建立 AND/OR/NOT 树，不能把 OR 改为 AND。
4. 确定基准日：新颖性优先采用用户给定的本案优先权日，其次申请日；用户明确尚未申请时采用请求中的当天日期。日期信息互相矛盾或申请状态不明时记录待确认，不猜日期。独立运行缺必要基准日时先补齐；被调用运行可置 null 并在 `needs_human` 写明，日期判断保持 UNKNOWN。全景不设截止日；侵权风险使用请求中的当前日期及中国有效、审中范围。
5. 确定 `read_scope`：默认 `full`；调用方明确给 `claims` 或 `biblio` 时原样保留。全景与侵权风险后续路径由程序选择，不借阅读范围自行启动全文匹配。
6. L4 交接：新任务按 `output_schema` 和下述外层结构写入任务包的 `result_path`，执行 `python run.py submit <run_id> SPEC <结果文件>`；修改任务把完整的新 spec 对象写入当前任务指定的结果文件，执行 `python run.py update-spec <run_id> <规格文件> --by <实际修改指示来源>`，此命令不接受外层封装。先核对只有用户指定字段发生变化，再提交；不能冒签用户姓名。校验失败只修正本阶段问题。独立新任务等待规格确认，被调用模式携带 `needs_human` 继续处理不依赖该项的内容。

## 5. 禁止动作（红线）

- 缺字段、材料不可得或来源冲突只能记 UNKNOWN（未知）；不能为了“减少候选”推断为 FAIL（不满足）。不确定条件按偏好处理，并写入 `needs_human`。
- 只有硬条件为 FAIL 才能支持排除；偏好不排除。不得擅自改动用户判定规则或阈值；不得修改预算、白名单或其他阶段产物。
- 公开日、申请日、优先权日不得替代。抵触申请候选单列待核实，不能直接当作普通匹配或直接排除。
- 肯定判定需同一公开文本、同一技术方案的逐字原文与位置；本阶段不产生证据，不以摘要、关键词共现或相似度作判定。
- 未公开技术内容不得发送到任务配置白名单外的数据源或模型服务；本阶段不操作网站，不直接调用其他 Skill。
- 不改运行状态、日志、原始材料、其他用户文件；三类结果及数量守恒由程序计算。

## 6. 输出要求

新任务结果使用统一封装：`{"task_token":"原样复制当前任务包值","model":"codex","context_id":"实际上下文标识","elapsed_seconds":0,"output":{...}}`。只把规格 JSON 放入 `output`，不直接编辑数据库；修改任务的 `update-spec` 文件只包含规格 JSON 本身。

`output` 必含 `entry`、`intent`、`base_date`、`read_scope`、`keys`、`features`、`hard`、`soft`、`needs_human`。`keys` 保存 lookup 号码，search 通常为空；`features` 每项含稳定的 `fid` 和完整 `text`。不要增加 Schema 没有的字段。缺项说明必须能让用户直接回答，例如“请确认 2024-06-01 是申请日还是优先权日”。

模型服务标识沿用当前任务包批准的 `model`（首版为 `codex`）；`elapsed_seconds` 填实际 Agent 工作秒数，不包括等待用户的时间，示例中的 0 不能替代计时。`context_id` 必须真实对应本次执行上下文。

## 7. 完成标准

- L5：所有明确的必要条件都有落点；全部逻辑树特征引用存在；不存在重复 `fid` 或未经确认的新硬条件；程序提交校验通过。
- L6：由程序记录输入快照、Skill 版本、实际模型与提交日志。不要伪造上下文标识或手工补写成功日志。
- `needs_human` 非空可以完成本阶段整理，但不表示歧义已解决；后续是否等待由调度器决定。

## 8. 示例

需求：“气体异常和电压突降同时发生才报警，储能场景优先。”正确：F1 气体检测、F2 电压突降检测、F3 二者同时满足才报警；F1–F3 是必要技术条件，“储能”是偏好。错误：把“储能”变为硬条件，或省略 F3，使分别具备两个传感器的文献也能通过。
